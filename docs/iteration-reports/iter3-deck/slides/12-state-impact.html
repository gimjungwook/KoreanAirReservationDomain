SEAT LIFECYCLE
Seat — hold 만료 자동 해제
Available → Held → Booked → Occupied
iter3 신규 전이 Held → Available · SeatHoldMonitor.sweep()
→ SeatHoldExpiredEvent publish
→ ReservationHoldListener.onEvent → seat.release()
Seat 신규 필드 holdExpiresAt : LocalDateTime
heldByPnr : String
isHoldExpired() : boolean
핵심 — 만료 판정은 Seat 본인이 하고, 부수효과(예약 취소)는 listener가 가져간다. Seat이 Reservation을 직접 알지 못한다.
FLIGHT SCHEDULE LIFECYCLE
FlightSchedule — 전파 책임 분리
Scheduled → Delayed → BoardingOpen → Departed → Arrived
Scheduled / Delayed → Cancelled
iter3 전이 부수효과 changeStatus(newStatus) — 모든 전이에서
→ FlightStatusChangedEvent(prev, new) publish
→ AffectedReservationListener 가 registry.all() 순회
왜 1:N 전파인가 한 schedule을 itinerary에 포함하는 Reservation이 N개. DELAYED · CANCELLED · DEPARTED 어떤 상태든 모든 N에게 통지가 필요. Observer가 정확히 1-to-N notification 시나리오.
핵심 — FlightSchedule이 ReservationRegistry를 직접 알지 않는다. publish만 하고, listener가 registry를 owns한다.
