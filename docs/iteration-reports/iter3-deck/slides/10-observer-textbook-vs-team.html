교과서 (GoF) · BEHAVIORAL
Observer Pattern

한 객체의 상태가 변할 때 그것에 의존하는 모든 객체에게 통지되어 자동으로 갱신되도록 하는 1-to-N 의존성을 정의한다.

Subject
관찰 대상. attach, detach, notify API
Observer
통지 인터페이스. update(subject) 추상 메서드
ConcreteSubject
실제 상태 변경 클래스. 변경 시 notify 호출
ConcreteObserver
Observer 구현체. update에서 subject 상태 가져와 갱신
왜 쓰나 — Subject와 Observer를 느슨하게 결합. Subject가 Observer 구현 클래스를 몰라도 통지 가능. 새 Observer 추가가 Subject 코드 수정 없이 가능 (OCP).
팀 A · iter3 적용
3개 Subject · 3개 Listener

좌석 hold 만료 · 결제 실패 · 항공편 변경 — 모두 "발행자는 부수효과를 모르고, listener가 자신의 책임만 수행"하는 구조로 통일.

Subject (base)
EventPublisher abstract — subscribe / unsubscribe / publish
Observer (base)
EventListener interface — onEvent(DomainEvent)
ConcreteSubject
SeatHoldMonitor · PaymentProcessor · FlightSchedule
ConcreteObserver
ReservationHoldListener · AutoCancelListener · AffectedReservationListener
Event payload
push-model — DomainEvent 서브클래스가 데이터 담아 전달
왜 도입했나 — iter2까지는 호출자(BookingController)가 부수효과를 매번 직접 호출했다. iter3에서 동일 트리거가 3개로 늘면서 호출자가 비대해졌고, Observer로 부수효과를 listener에 위임해 단일 책임으로 분리.
